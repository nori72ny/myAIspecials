# V1.4 Coding Readiness UI

The Coding workspace renders only non-secret readiness metadata already returned by `/api/coding/v1.4/status`.

It shows controller/control-plane readiness, database/store configuration, live schema reachability, owner binding, encryption readiness, dedicated Coding authorization, GitHub dispatch readiness, and the worker opt-in flag.

The UI does not render environment values, database URIs, bearer credentials, GitHub tokens, encryption keys, owner HMAC material, or secret-derived diagnostics. Missing prerequisites keep new submissions fail-closed. Existing owner-scoped job lookup/cancellation remains governed by the narrower human-control boundary already implemented in V1.4.

This visibility improvement does not add Git publication, deployment authority, paid fallback, or Claude Code parity claims.

## Truthful status and Japanese interactions (2026-09-12)

Configuration readiness is labelled 設定確認済み and explicitly does not prove worker execution. Connection and diagnostic details use native collapsible sections. Main request, reconnect, cancellation and job-state labels are Japanese. Safe allowlisted dispatch error codes receive Japanese explanations; raw provider messages are never displayed and no automatic submission retry is added.

Removed invented lifecycle percentages and inferred completed-stage tiles: a cancelled/blocked job can stop before editing, so terminal state alone cannot prove earlier stages ran. Display the returned job state with its meaning and retain the actual verification checks/diffs. An unsuccessful HTTP status or an application response without `ok: true` cannot enable submission.

Tests cover permission-denied messaging, absence of provider response leakage/retries, unsuccessful readiness responses, and cancellation before claim without fictional progress. Navigation tests follow the Japanese accessible labels.
