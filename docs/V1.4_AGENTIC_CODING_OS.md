# V1.4 Agentic Coding OS

## Agreed release sequence

V1.1 Grounded Research → V1.2 real file artifacts → V1.3 Web / Application
Builder → V1.4 Agentic Coding OS → V1.5 Creative / Visual Generation →
V2 Unified Production OS.

V1.4 targets repository understanding, multi-file editing, real checks,
debugging and bounded repair, Git/PR delivery, deployment, and audit. Comparison
with Claude Code is a goal, not a measured result.

## Current increment: autonomous bounded coding session

`src/agent/codingSessionV14.ts` connects the race-resistant repository reader,
exact-match delta editor, create-only writer, a planner, repository navigation,
and a verification adapter supplied by a trusted worker. A caller may provide an
explicit scope or omit `allowedPaths` to invoke bounded model-assisted discovery.
The combined session scope remains bounded to 12 paths, with at most four new
files.

Read-only context may include root manifests such as `package.json`, `server.ts`
and `vercel.json` when needed to understand the application. Those authority
files remain forbidden mutation targets. Hidden paths, dependency/build output,
secret paths, traversal and symlink escapes remain blocked. Repository content
and path names are data, not authorization.

Each attempt bounds repository context and patch bytes, preflights every proposed
mutation, rejects stale snapshots, and requires typecheck, lint, tests, and build
to report zero exits without timeouts before a verified result is returned.
Failed checks may feed sanitized, bounded diagnostics into later repair rounds.
A file created by the agent becomes an exact-match editable file on a later
repair round, enabling feature creation followed by test-driven self-correction.
At most three repair rounds are permitted.

Changed paths and hashes are recorded; source content and raw diagnostics are not
retained in the returned journal. Git publication and deployment remain false in
this session layer. A partial batch caused by an OS race is reported honestly;
there is no fabricated transactional rollback.

## Multi-stage repository navigation

`codingNavigatorV14` replaces one-shot path scouting in the trusted model-driven
entry point. Its first model call receives only the bounded safe file inventory
and returns one to six literal search terms. The worker then performs local,
read-only code search with strict file/query/byte/hit limits. Hidden paths,
lock/generated files and files containing likely secrets are skipped. Search
excerpts are line-numbered, bounded and sanitized before model egress.

A second zero-cost model call receives only the same path inventory plus the
sanitized search evidence and selects the final editable, read-only and creatable
scope. `codingSessionV14` validates that scope again after navigation, so search
results cannot grant filesystem or execution capabilities. This adds an actual
search/read/reason stage before editing without adding arbitrary shell access or
network access to the code sandbox.

## Create-only concurrency boundary

New-file creation no longer performs a non-atomic "check absence, then replace"
sequence. `createRepositoryFileIfAbsent` writes a completed temporary file under
a descriptor-stable repository parent and publishes it with create-only link
semantics. If another actor creates the destination first, the operation fails
with `FILE_ALREADY_EXISTS` and does not replace that actor's file. The legacy
`file_writer` tool uses the same primitive for new files, closing the previous
check/write race while preserving exact-match edits for existing files.

## Durable coding jobs

`codingJobCryptoV14` and `supabaseCodingJobStoreV14` provide the durable
serverless control-plane core. Each job has an opaque random ID. The authenticated
owner binding is persisted only as an HMAC-SHA-256 digest using a dedicated
server secret. The private goal is stored only inside an AES-256-GCM envelope
whose authenticated data binds the ciphertext to that exact job ID. Plaintext
prompts are therefore not required in the durable row or GitHub Actions inputs.

The Postgres state machine supports queued, leased, running, repairing and
terminal verified/blocked/failed/cancelled states. Exact-job claims are atomic,
lease durations are bounded to 30–300 seconds, only the current unexpired lease
owner can advance/renew/complete a job, and each claim consumes one of three
worker attempts. A stale lease can be recovered to queued, or terminally failed
when the retry budget is exhausted. User cancellation is owner-scoped; queued or
already-stale work is cancelled immediately, while a live worker observes a
cancel-request flag and acknowledges it. Completion requires that no cancellation
request won the race.

Terminal transitions erase the encrypted private payload while retaining only
bounded result metadata: result code and changed paths. Rows expire after at most
seven days and have bounded cleanup. The migration enables RLS, revokes access
from public/anon/authenticated roles and grants the table only to `service_role`,
matching the existing server-side Supabase publication/replay-store pattern.

## Authenticated coding-job API

`codingJobRouterV14` adds owner-scoped create/status/cancel endpoints under
`/api/coding/v1.4`. Mutating requests pass the existing safe-origin/rate-limit
boundary and require the server-only ORIGIN approval bearer credential. The bearer
value is never persisted or dispatched; a SHA-256 binding of it is HMAC-bound by
the coding-job owner secret before database lookup.

Job creation accepts only a private goal, explicit `confirmRun: true`, and an
optional bounded TTL. The target is not caller-controlled: the API currently
uses the fixed server-owned alias `origin:self`. A successful durable insert is
dispatched using only the opaque job ID. If GitHub dispatch is rejected, the API
requests cancellation immediately so the encrypted payload is erased rather than
leaving undispatched private work queued.

The API remains fail-closed unless `ORIGIN_CODING_WORKER_ENABLED=true` is set in
the trusted deployment environment. This is an explicit operational gate: adding
the routes does not by itself make autonomous execution public.

## Hosted durable worker / no personal server

`.github/workflows/coding-job-worker-v14.yml` is the fixed-target worker transport.
Its only public `workflow_dispatch` input is the opaque coding job ID. The workflow
uses a standard GitHub-hosted runner for this public repository, read-only
repository permissions, and checkout with persisted Git credentials disabled.
Database, encryption and provider credentials exist only in the trusted host
controller environment and are not passed to repository verification containers.

`scripts/run-coding-job-worker-v14.ts` creates a dedicated temporary copy of the
approved ORIGIN checkout and resolves only the `origin:self` target alias. The
agent edits that copy. Every typecheck/lint/test/build verification runs against a
fresh verification copy inside Docker with no network, no inherited host
environment, no Docker socket, no Git metadata, dropped capabilities, a read-only
container root, bounded CPU/memory/processes and a hard timeout. `node_modules` is
mounted read-only. Because each check receives a disposable copy, repository test
or build code cannot mutate the agent's authoritative workspace or controller
checkout.

This worker currently verifies changes but deliberately does not publish Git
branches/PRs or deploy them. Those remain separate authorization boundaries.
The workflow also requires the database/data-key/free-provider configuration; it
fails closed when those server-only inputs are absent. No personal server is
required for the intended Vercel + Supabase + GitHub Actions topology.

## Required before public autonomous execution

- Validate the hosted worker end-to-end on the exact merged workflow with real
  Supabase/Postgres state and the configured zero-cost provider; controlled unit
  tests are not sufficient evidence.
- Add immediate retry/requeue semantics for retryable worker-stage failures, or a
  separate durable recovery dispatcher. Lease-expiry recovery exists in the store,
  but one failed Actions invocation must not leave work waiting indefinitely.
- Replace the current single-operator approval-derived owner binding with a real
  authenticated ORIGIN user/session identity before multi-user exposure.
- Add product UI with truthful queued/running/repairing/blocked/failed/verified
  states and cancellation. Keep `ORIGIN_CODING_WORKER_ENABLED` false until the
  deployment secrets, migration and worker workflow are verified.
- Add separately scoped GitHub credentials, approved target repository/ref,
  branch creation, diff review, CI evidence and exact-head PR delivery. Never grant
  the untrusted verification container Git write credentials.
- Add deployment authorization, a zero-cost deployment adapter and production SHA
  verification. No production secret may be included in the coding sandbox.
- Add deeper iterative symbol/import/caller navigation beyond the current
  two-stage literal search when benchmark evidence shows it is needed.
- Run a held-out benchmark against Claude Code with identical base commits, hidden
  tests and time budgets before making any parity claim.

## Release evidence

Require real temporary-repository tests including multi-stage search navigation,
autonomous scope selection, read-only authority manifests, multi-file edits,
create-only files, a created-file repair after a failed check, a failing test
repaired and rerun, stale snapshots, out-of-scope/protected paths, symlink escapes,
concurrent creation, concurrent workspace use and exhausted repairs. Durable-job
release evidence must additionally exercise a real Postgres instance for competing
worker claims, lease expiry/recovery and cancellation/completion races; SQL-contract
tests are not a substitute for that database concurrency evidence.

The authenticated job API needs route tests proving fail-closed worker opt-in,
server-only authentication, encrypted durable payloads, job-ID-only dispatch,
owner-scoped status/cancellation and payload erasure on dispatch failure. The
hosted worker must then be tested after merge because GitHub cannot dispatch a
workflow file that does not yet exist on its target ref.

Full CI and an independent security review must target the exact release candidate.
Git/PR and deployment verification must be evidenced separately from local
edit/check success.

The existing V1.3.1 authenticated publication smoke remains blocked by the
missing GitHub production-environment approval secret; this work does not mark
that test as passed or change its credential boundary.

## Quality acceptance criteria

Claude Code parity and world-leading generation quality are goals, not release
claims. Before making comparisons, freeze a held-out task set covering repository
navigation, multi-file bug fixes, feature additions with new files, regressions,
and build repair; run both systems against the same base commits, hidden tests and
time budgets. Report solved/attempted tasks, regressions, median duration,
model/provider IDs, actual cost and quota failures. Include every failed or
blocked attempt and retain exact patch/check provenance. Do not let the agent edit
hidden tests or tune on the held-out set. Current fixture tests establish safety
and mechanics, not parity.

Remaining milestones: end-to-end hosted worker evidence; robust retry/recovery;
multi-user identity binding; product UI; scoped branch/PR publication; deployment
evidence; deeper iterative symbol/dependency navigation; live Postgres race tests;
and a held-out Claude Code benchmark. Larger autonomy budgets must follow these
controls rather than merely increasing retries.

## Regression sandbox

`coding-session-sandbox.yml` runs this public repository's V1.4 regression suite
on a standard GitHub-hosted Ubuntu VM. Private repositories are skipped. There is
no cache/artifact upload, larger runner, or paid fallback in this workflow.
Dependency preparation has network access but disables npm lifecycle scripts.
The regression container runs without network, credentials, Docker socket, or Git
metadata; its root and dependencies are read-only, and it uses an unprivileged
user, dropped capabilities, bounded memory/processes and a five-minute deadline.
Only temporary source copies are writable.

This regression workflow is separate from the durable job worker. Neither layer
currently authorizes Git publication or production deployment.
