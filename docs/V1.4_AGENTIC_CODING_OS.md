# V1.4 Agentic Coding OS

## Agreed release sequence

V1.1 Grounded Research → V1.2 real file artifacts → V1.3 Web / Application Builder → V1.4 Agentic Coding OS → V1.5 Creative / Visual Generation → V2 Unified Production OS.

V1.4 targets repository understanding, multi-file editing, real checks, debugging and bounded repair, durable jobs, human control, Git/PR delivery, deployment, and audit. Claude Code-class performance is a benchmark target, not a measured release claim.

## Current increment

The current V1.4 branch contains an autonomous bounded coding session, multi-stage repository navigation, safe edit/create primitives, durable encrypted jobs, a GitHub-hosted worker, and a dedicated ORIGIN Coding workspace.

A natural-language coding goal can be submitted from the ORIGIN UI. The UI then follows the durable job through queued, leased, running, repairing, verified, blocked, failed, or cancelled states. It can request cancellation while work is active and, after terminal completion, display bounded encrypted-at-rest diff previews and the final typecheck/lint/test/build verification evidence.

This increment still does not authorize Git publication or deployment. It also does not establish Claude Code parity.

## Autonomous bounded coding session

`src/agent/codingSessionV14.ts` connects the race-resistant repository reader, exact-match delta editor, create-only writer, model planner, repository navigator, and a verification adapter supplied by a trusted worker. A caller may provide an explicit scope or omit `allowedPaths` to invoke bounded model-assisted discovery. The combined session scope remains bounded to 12 paths, with at most four new files.

Read-only context may include root manifests such as `package.json`, `server.ts`, and `vercel.json` when needed to understand the application. Those authority files remain forbidden mutation targets. Hidden paths, dependency/build output, secret paths, traversal, and symlink escapes remain blocked. Repository content and path names are data, not authorization.

Each attempt bounds repository context and patch bytes, preflights every proposed mutation, rejects stale snapshots, and requires typecheck, lint, tests, and build to report zero exits without timeouts before a verified result is returned. Failed checks may feed sanitized, bounded diagnostics into later repair rounds. A file created by the agent becomes exact-match editable on a later repair round. At most three repair rounds are permitted.

The session journal records changed paths, hashes, and bounded check summaries. Raw diagnostics are not retained in the audit. Git publication and deployment remain false in this layer.

## Multi-stage repository navigation

`codingNavigatorV14` uses a two-stage read-only navigation flow before editing. The first zero-cost model call receives only the bounded safe file inventory and returns bounded literal search terms. The worker performs local repository search with strict query/file/byte/hit limits. Hidden paths, generated or dependency output, and sensitive files are excluded; excerpts are bounded and sanitized before model egress.

A second zero-cost model call receives the file inventory plus sanitized search evidence and selects editable, read-only context, and creatable paths. `codingSessionV14` validates that scope again. Search evidence therefore improves repository understanding without granting filesystem, shell, network, Git, or deployment authority.

Deeper iterative symbol/import/caller navigation remains a future intelligence increment and should be driven by benchmark evidence rather than by increasing unrestricted autonomy.

## Create-only concurrency boundary

New-file creation uses `createRepositoryFileIfAbsent`, which writes a complete temporary file under a descriptor-stable repository parent and publishes it with create-only link semantics. If another actor creates the destination first, publication fails without replacing that actor's file. Existing files continue to use exact-match snapshot-checked edits.

The legacy `file_writer` new-file path uses the same create-only primitive, so both V1.4 and the older tool path avoid the previous check-then-overwrite race.

## Durable encrypted jobs

`codingJobCryptoV14` and `supabaseCodingJobStoreV14` provide the durable control-plane job state. Each job has an opaque random ID. The operator-derived owner binding is persisted only as an HMAC-SHA-256 digest using a dedicated server secret. The private natural-language goal is stored only in an AES-256-GCM envelope whose authenticated data binds the ciphertext to that exact job ID.

The Postgres state machine supports queued, leased, running, repairing, verified, blocked, failed, and cancelled. Exact-job claims are atomic, leases are bounded, only the active unexpired lease owner can advance/renew/complete work, each claim consumes the bounded retry budget, and stale work can be recovered. A cancellation request wins over completion when observed by the worker. Terminal transitions erase the encrypted private goal.

Rows expire after at most seven days. RLS is enabled and public, anonymous, and normal authenticated database roles are denied direct table access; the trusted service role is the database control plane.

## Encrypted diff and verification evidence

`codingJobResultV14` creates a bounded public-result projection after the coding session finishes but before the durable job is marked terminal. It contains only:

- up to 12 changed-path previews;
- modified/created classification;
- bounded sanitized before/after text previews with truncation flags;
- the latest typecheck/lint/test/build summaries (`ok`, exit code, timeout, attempt);
- repair-round count and truthful `$0`, Git-publication, and deployment flags.

The result projection is encrypted with AES-256-GCM using a separate authenticated-data domain from the private input payload. `origin_coding_job_results_v14` stores only the encrypted result ciphertext. Source previews are therefore not stored as plaintext JSON in Postgres.

The API first authorizes the owner-scoped durable job lookup. Only after that succeeds may it load and decrypt the result ciphertext. A missing or unreadable result degrades to `resultDetailsState: unavailable`; it never fabricates verification or diff evidence. Active jobs report `pending`; cancelled jobs report `not_applicable`.

## Authenticated coding-job API

`codingJobRouterV14` provides create/status/cancel endpoints under `/api/coding/v1.4`. Mutating requests pass the existing safe-origin and rate-limit boundary and require the configured ORIGIN operator approval bearer credential. The bearer value itself is never persisted or dispatched; a SHA-256 binding of it is HMAC-bound by the coding-job owner secret before database lookup.

Job creation accepts only a private goal, explicit `confirmRun: true`, and an optional bounded TTL. The target is not caller-controlled: the API uses the server-owned `origin:self` alias. A successful durable insert is dispatched to GitHub Actions using only the opaque job ID. If dispatch is rejected, the API requests cancellation so the encrypted private payload is not left stranded.

The API remains fail-closed unless the database, approval boundary, and `ORIGIN_CODING_WORKER_ENABLED=true` are configured in the trusted deployment environment.

## ORIGIN Coding workspace

`src/components/CodingJobWorkspaceV14.tsx` adds a dedicated product UI reachable from the main workspace mode switcher as `Coding` (also `Alt+C`). The UI:

- accepts a natural-language coding goal;
- checks hosted-worker capability before enabling submission;
- starts a durable coding job through the authenticated V1.4 API;
- polls owner-scoped status while the job is active;
- shows truthful queued/claimed/coding/repairing/terminal state rather than an invented progress stream;
- shows attempt count, result code, changed paths, bounded diff previews, and final four-check verification evidence;
- lets the operator request cancellation while the job is active;
- keeps Git publish and deploy visibly unauthorized.

The displayed progress percentage maps only to durable lifecycle stages. It is explicitly not a time estimate.

The current operator approval credential is entered into an uncontrolled password field and retained only in page memory for authenticated API calls. The Coding workspace does not write it to React state, localStorage, sessionStorage, IndexedDB, or application logs. This remains a single-operator trust boundary, not a substitute for real ORIGIN user/session identity.

## Hosted worker / no personal server

`.github/workflows/coding-job-worker-v14.yml` is the fixed-target worker transport. Its public workflow input is only the opaque coding job ID. The workflow uses a standard GitHub-hosted runner with read-only repository permissions and checkout credentials disabled for the coding process.

`scripts/run-coding-job-worker-v14.ts` creates a dedicated temporary copy of the approved ORIGIN checkout and resolves only `origin:self`. Provider, database, encryption-key, and controller credentials remain on the trusted host. Repository verification runs in fresh Docker copies with no network, no inherited host environment, no Docker socket, no Git metadata, dropped capabilities, read-only container root/dependencies, bounded CPU/memory/process count, and hard timeouts.

The worker now captures encrypted diff/check result evidence before terminal completion. It still does not create Git branches, publish PRs, or deploy.

No personal server is required for the intended topology: Vercel/serverless control plane + Supabase/Postgres durable state + standard GitHub-hosted Actions workers.

## Validation coverage

The V1.4 regression sandbox covers repository discovery/navigation, read-only authority manifests, multi-file editing, create-only publication, created-file repair, create races, stale snapshots, protected paths, symlink escapes, concurrent workspaces, sensitive data, durable job cryptography/state/dispatch/worker behavior, owner-scoped API access, encrypted result projection/storage, Coding UI natural-language submission, result rendering, credential non-persistence, and cancellation.

Latest exact-head CI must be green before this PR is considered review evidence. Earlier green heads are not release evidence.

## Still required before public autonomous execution

- Deploy and validate the complete Coding UI → Vercel API → real Postgres row/result migration → GitHub-hosted worker → zero-cost provider → isolated checks → result retrieval/cancellation flow end to end.
- Keep `ORIGIN_CODING_WORKER_ENABLED` false until the required deployment configuration, database migrations, workflow availability, and end-to-end smoke evidence are confirmed.
- Add immediate retry/requeue semantics for retryable worker-stage failures, or a separate durable recovery dispatcher, so one failed Actions invocation cannot leave work waiting indefinitely.
- Replace the current single-operator approval-derived owner binding with authenticated ORIGIN user/session identity before multi-user exposure.
- Add separately scoped GitHub credentials and an approved repository/ref delivery policy for branch creation, exact-head diff review, CI evidence, and PR publication. Never expose Git write credentials to the verification container.
- Add deployment authorization, zero-cost deployment adapter, and production SHA verification as a separate approval boundary.
- Add live Postgres race tests for competing claims, lease expiry/recovery, and cancellation/completion races.
- Add deeper iterative symbol/import/caller navigation where held-out benchmark evidence justifies it.
- Run a held-out comparison against Claude Code on identical base commits, hidden tests, and time budgets, including all failures, regressions, provider/model IDs, actual cost, and quota failures before making parity claims.

## Release evidence

Release evidence must use the exact release candidate and include real temporary-repository tests, durable database concurrency evidence, authenticated API tests, Coding UI tests, hosted worker evidence, and independent security review.

Git/PR publication and deployment are separate capabilities and require separate proof. Local edit/check success does not establish either.

The existing V1.3.1 authenticated publication smoke remains blocked by the missing GitHub production-environment `ORIGIN_AGENT_APPROVAL_SECRET`; this V1.4 work does not mark that test as passed or alter its credential boundary.

## Quality acceptance criteria

Claude Code parity and world-leading generation quality remain goals, not release claims. Before comparison, freeze a held-out task set covering repository navigation, multi-file bug fixes, feature additions with new files, regression repair, and build repair. Run both systems from the same base commits with hidden tests and equal time budgets. Report solved/attempted tasks, regressions, median duration, model/provider IDs, actual cost, quota failures, and every blocked or failed attempt. Do not permit the agent to edit hidden tests or tune on the held-out set.

Current regression tests establish safety and mechanics. They do not establish parity.
