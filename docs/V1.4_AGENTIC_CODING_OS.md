# V1.4 Agentic Coding OS

## Agreed release sequence

V1.1 Grounded Research → V1.2 real file artifacts → V1.3 Web / Application
Builder → V1.4 Agentic Coding OS → V1.5 Creative / Visual Generation →
V2 Unified Production OS.

V1.4 targets repository understanding, multi-file editing, real checks,
debugging and bounded repair, Git/PR delivery, deployment, and audit. Comparison
with Claude Code is a goal, not a measured result.

## Current increment: autonomous bounded coding session

`src/agent/codingSessionV14.ts` connects the race-resistant repository reader,
exact-match delta editor, create-only writer, a planner, repository scope scout,
and a verification adapter supplied by a trusted worker. A caller may provide an
explicit scope or omit `allowedPaths` to invoke bounded model-assisted discovery.
The discovery model receives only the protected repository file inventory, never
file contents; it can select existing editable files, read-only context, and a
small set of genuinely new creatable paths. The combined session scope remains
bounded to 12 paths, with at most four new files.

Read-only context may include root manifests such as `package.json`, `server.ts`
and `vercel.json` when needed to understand the application. Those authority
files remain forbidden mutation targets. Hidden paths, dependency/build output,
secret paths, traversal and symlink escapes remain blocked. Repository content
and path names are data, not authorization.

Each attempt bounds repository context and patch bytes, preflights every proposed
mutation, rejects stale snapshots, and requires typecheck, lint, tests, and build
to report zero exits without timeouts before a verified result is returned.
Failed checks may feed sanitized, bounded diagnostics into later repair rounds.
A file created by the agent becomes an exact-match editable file on a later
repair round, enabling feature creation followed by test-driven self-correction.
At most three repair rounds are permitted.

Changed paths and hashes are recorded; source content and raw diagnostics are not
retained in the returned journal. Git publication and deployment remain false in
this session layer. A partial batch caused by an OS race is reported honestly;
there is no fabricated transactional rollback.

## Create-only concurrency boundary

New-file creation no longer performs a non-atomic "check absence, then replace"
sequence. `createRepositoryFileIfAbsent` writes a completed temporary file under
a descriptor-stable repository parent and publishes it with create-only link
semantics. If another actor creates the destination first, the operation fails
with `FILE_ALREADY_EXISTS` and does not replace that actor's file. The legacy
`file_writer` tool uses the same primitive for new files, closing the previous
check/write race while preserving exact-match edits for existing files.

## Required before public autonomous execution

- A dedicated runner with OS/process/network isolation, job deadline, bounded
  output and process-tree termination. Sanitizing environment variables alone
  is **not** a sandbox. Do not expose the existing `process.cwd()` writer or
  verification runner to user-supplied repositories on the production app.
- Live validation of the zero-cost scout/planner adapters and their structured
  scope/patch outputs. Current protocol tests use controlled provider responses,
  not a live model benchmark.
- A durable job store and independent worker leases, authenticated ownership,
  cancellation, restart recovery and retention/deletion controls.
- Separately scoped GitHub credentials, approved target repository/ref, branch
  creation, diff review, CI evidence and exact-head PR delivery.
- Deployment authorization, a zero-cost deployment adapter and production SHA
  verification. No production secret may be included in the coding sandbox.
- Product UI with truthful pending/running/blocked/failed/verified states and
  cancellation. V1.4 must not be labeled complete while these are unavailable.

## Release evidence

Require real temporary-repository tests including autonomous inventory discovery,
read-only authority manifests, multi-file edits, create-only files, a created-file
repair after a failed check, a failing test repaired and rerun, stale snapshots,
out-of-scope/protected paths, symlink escapes, concurrent creation, concurrent
workspace use and exhausted repairs. Full CI and an independent security review
must target the exact release candidate. Git/PR and deployment verification must
be evidenced separately from local edit/check success.

The existing V1.3.1 authenticated publication smoke remains blocked by the
missing GitHub production-environment approval secret; this work does not mark
that test as passed or change its credential boundary.

## Model-driven discovery and repair

`runCodingAgentV14` connects both scope scouting and implementation planning to
the existing zero-cost provider client. The trusted controller holds provider
credentials and supplies an isolated verification adapter. The scout sees only a
bounded list of repository paths. After scope selection, the planner sees only
the selected file contents, authorized mutable/create paths, repair diagnostics,
and the user goal. Both adapters require strict JSON and verified zero-cost
execution evidence. No paid fallback is added.

This materially improves autonomy over the prior V1.4 increment: the caller no
longer has to know every file that should be edited, the agent can add new source
files, and newly created files participate in later verification-driven repair.
It still does not authorize arbitrary shell commands, network access, package
changes, deployment configuration changes, Git publication, or production UI
execution.

### Quality acceptance criteria

Claude Code parity and world-leading generation quality are goals, not release
claims. Before making comparisons, freeze a held-out task set covering repository
navigation, multi-file bug fixes, feature additions with new files, regressions,
and build repair; run both systems against the same base commits, hidden tests and
time budgets. Report solved/attempted tasks, regressions, median duration,
model/provider IDs, actual cost and quota failures. Include every failed or
blocked attempt and retain exact patch/check provenance. Do not let the agent edit
hidden tests or tune on the held-out set. Current fixture tests establish safety
and mechanics, not parity.

Remaining milestones: durable jobs with cancel/resume; authenticated ORIGIN UI
dispatch and result retrieval; scoped branch/PR publication; deployment evidence;
stronger multi-stage repository navigation/content search; and a live held-out
model benchmark. Larger autonomy budgets must follow these controls rather than
merely increasing retries.

## Hosted runner increment (no personal server)

`coding-session-sandbox.yml` runs this public repository's session regression
suite on a standard GitHub-hosted Ubuntu VM. Private repositories are skipped.
There is no cache or artifact upload, larger runner, or paid fallback in this
workflow. Public standard runner minutes are free under GitHub's documented
billing policy: https://docs.github.com/en/billing/concepts/product-billing/github-actions.

Dependency preparation has network access but disables npm lifecycle scripts.
The test container runs without network, credentials, Docker socket, or Git
metadata; its root and dependencies are read-only, and it uses an unprivileged
user, dropped capabilities, bounded memory/processes and a five-minute deadline.
Container removal terminates remaining processes after timeout. Only temporary
source copies are writable. The Node image uses a version tag, not an immutable
digest; dependency supply-chain review remains a production runner requirement.

This is CI evidence for the coding-session core, not an arbitrary-code service
or a production dispatch adapter. Public workflow logs must never receive private
tasks or source. User ownership, authenticated dispatch, durable job state and
result retrieval still need implementation before enabling remote coding from the
ORIGIN UI. No personal server is required for this route.
