# V1.4 Production Activation Checklist

This checklist is the operational handoff for turning the already-implemented V1.4 Agentic Coding OS from fail-closed production state into a live end-to-end path. It does not authorize Git publication or deployment and does not establish Claude Code parity.

## Current verified baseline

- `main` contains the durable coding API, encrypted Postgres job/result stores, GitHub-hosted worker path, isolated verification, cancellation, and Coding UI.
- The Coding UI can reopen an existing opaque job after page reload without persisting the job ID or credential.
- Production Supabase already contains `origin_coding_jobs_v14` and `origin_coding_job_results_v14`, with RLS enabled and the cancellation cleanup trigger present.
- The current Vercel production runtime remains intentionally fail-closed because no supported PostgreSQL URI is currently parseable there and the remaining coding secrets/dispatch opt-in are not all ready.

## Vercel production variables

Configure these in the Vercel **production** environment. Never commit their values to Git, paste them into issues/PRs, or expose them to browser code.

1. One valid PostgreSQL connection URI, using the first parseable supported candidate:
   - `POSTGRES_URL`, or
   - `DATABASE_URL`, or
   - `SUPABASE_DB_URL`.

   The URI must parse successfully, use `postgres:` or `postgresql:`, and contain a host. Malformed candidates are skipped by the resolver. Prefer one explicit valid setting and remove stale values to avoid ambiguity; a syntactically valid URL with incorrect credentials still needs a live connection check.

2. `ORIGIN_CODING_OPERATOR_SECRET`
   - preferred dedicated browser-facing Coding credential;
   - once configured, invalid Coding credentials fail closed and do not fall back to `ORIGIN_AGENT_APPROVAL_SECRET`.

3. `ORIGIN_CODING_JOB_OWNER_HMAC_SECRET`
   - dedicated stable owner-binding secret;
   - used to HMAC the server-defined single-operator owner identity before persistence.

4. `ORIGIN_CODING_JOB_DATA_KEY`
   - AES-256-GCM data key for private goals and encrypted result evidence;
   - must match the worker-side value exactly.

5. `ORIGIN_CODING_GITHUB_DISPATCH_TOKEN`
   - server-only token used by Vercel to dispatch the fixed workflow on `main`;
   - the public workflow payload must remain only `{ job_id: <opaque id> }`.

6. `ORIGIN_CODING_WORKER_ENABLED=true`
   - set this **last**, only after every prerequisite below is verified;
   - leaving it false keeps new job submission fail-closed while preserving the narrower human-control boundary when its prerequisites are available.

## GitHub Actions repository secrets

The fixed `.github/workflows/coding-job-worker-v14.yml` currently requires these repository secrets:

- `POSTGRES_URL`
- `ORIGIN_CODING_JOB_DATA_KEY`
- `OPENROUTER_API_KEY`

The workflow has read-only repository permission, uses `persist-credentials: false`, and does not receive Git write credentials. The verification container must never receive these host credentials.

The worker-side `POSTGRES_URL` must reach the same production Supabase/Postgres database used by the Vercel control plane, and `ORIGIN_CODING_JOB_DATA_KEY` must be identical on both sides so encrypted job/result payloads remain interoperable.

## Activation order

Follow this order to avoid enabling a half-configured autonomous path:

1. Configure/repair the Vercel production PostgreSQL URI.
2. Configure `ORIGIN_CODING_JOB_OWNER_HMAC_SECRET`.
3. Configure the same `ORIGIN_CODING_JOB_DATA_KEY` in Vercel production and GitHub Actions secrets.
4. Configure `ORIGIN_CODING_OPERATOR_SECRET` in Vercel production.
5. Configure `POSTGRES_URL` and `OPENROUTER_API_KEY` for the GitHub worker.
6. Configure `ORIGIN_CODING_GITHUB_DISPATCH_TOKEN` in Vercel production.
7. Redeploy Vercel production and call `/api/coding/v1.4/status`.
8. Require `databaseReady`, `storeReady`, `resultStoreReady`, `authorizationReady`, `ownerBindingReady`, `dataKeyReady`, `cryptoReady`, and `dispatchReady` to be true, with `authorizationMode="coding-operator"`. At this stage `workerEnabled` and overall `ready` must remain false. `$0`, paid-fallback-disabled, Git-unpublished, and deployed-false claims remain unchanged.
9. Only then set `ORIGIN_CODING_WORKER_ENABLED=true` and redeploy.
10. Run one bounded authenticated production smoke from Coding UI through encrypted result retrieval/cancellation.
11. Record the exact production Git SHA, Vercel deployment ID, workflow run ID, result status, verification checks, actual model/provider identity, and actual cost/quota outcome.

## Expected status progression

Before database connectivity is fixed, the status endpoint may truthfully show:

- `databaseReady=false`
- `storeConfigured=false`
- `resultStoreConfigured=false`
- `ownerBindingReady=false`
- `dataKeyReady=false`
- `cryptoReady=false`
- `dispatchReady=false`
- `workerEnabled=false`
- `ready=false`

After database, owner binding, data key, Coding authorization, and dispatch are configured—but before the opt-in flag is enabled—new submission must still remain `ready=false` because `workerEnabled=false`.

After all prerequisites and `ORIGIN_CODING_WORKER_ENABLED=true` are live, the endpoint may report `ready=true` only if the live job/result schema probes also succeed. Configuration presence alone is not release evidence.

## Production smoke acceptance

A production smoke is acceptable only if all of the following are observed on the exact deployed SHA:

- Coding UI POST succeeds with the dedicated Coding credential.
- The Vercel API stores only encrypted private payload state in Postgres.
- GitHub workflow dispatch contains only the opaque job ID as public input.
- Worker claims the exact job through the durable store.
- Repository work runs on the standard GitHub-hosted runner under the existing `$0` boundary.
- Verification runs in the isolated Docker path with no network, no Git credentials, no host environment inheritance, and bounded resources/timeouts.
- Terminal result evidence is encrypted at rest and owner-scoped on retrieval.
- Cancellation wins correctly if requested and removes result evidence according to the existing database/API/worker cleanup defenses.
- `freeOnly=true`, `costUsd=0`, `paidFallbackEnabled=false`, `gitPublished=false`, and `deployed=false` remain truthful for this V1.4 path.

## Still outside V1.4 completion

The following remain separate capabilities and must not be implied by a successful coding smoke:

- multi-user authenticated ORIGIN identity replacing the current single-operator owner binding;
- Git branch/PR publication with separately scoped write credentials;
- deployment authorization and production SHA promotion;
- deeper benchmark-driven symbol/import/caller navigation;
- any Claude Code parity claim without an identical-base, hidden-test, equal-budget benchmark including failures, regressions, provider/model IDs, cost, and quota failures.
