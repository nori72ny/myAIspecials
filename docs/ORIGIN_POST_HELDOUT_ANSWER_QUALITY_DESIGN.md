# ORIGIN — Post-Held-Out Answer Quality Design Inputs

## Purpose

Prepare verified design inputs for the answer-quality phase without changing runtime behavior before the V1.4 final unseen held-out qualification.

This branch is planning-only. Do not merge it into main and do not wire any of these ideas into production before the held-out result is finalized.

## Current external reference set

### OpenAI

Current reference target is ChatGPT Work / Cloud Browser / Workspace Agents rather than the older ChatGPT Agent Mode naming.

Verified product patterns:
- Work can break goals into smaller steps and produce finished deliverables.
- Cloud Browser runs on a separate cloud computer and pauses for sign-in, confirmation, or user input.
- Users can inspect progress, redirect work, and approve important actions.
- Workspace Agents support repeatable workflows, tools, schedules, API triggers, and permission controls.

ORIGIN design input:
- keep conversation separate from delegated work;
- expose action-level progress and intervention;
- use isolated execution surfaces;
- preserve explicit approval boundaries;
- treat Work/Coding/Chat as separate experience layers.

### Perplexity

Verified product patterns:
- Pro Search conducts multiple web searches and synthesizes dozens of sources;
- the product exposes how it broke down the question;
- answers include direct source links and support iterative refinement.

Not yet verified:
- exact proprietary ranking formula;
- exact claim-to-citation generation algorithm;
- any assertion that citations are generated by one specific internal RAG implementation.

ORIGIN design input:
- multi-query research loop;
- source quality/freshness/relevance gates;
- explicit source-to-claim evidence records;
- follow-up research only when evidence is insufficient.

### Google Gemini

Verified product patterns:
- current Gemini thinking models reason internally before final output;
- APIs may expose encrypted thought signatures and optional thought summaries, not raw unrestricted internal reasoning;
- thinking depth can be controlled by model/API settings;
- Deep Think is a distinct stronger reasoning mode and Google describes parallel thinking for complex problems.

ORIGIN design input:
- do not expose hidden reasoning logs;
- expose concise action/reason summaries when useful;
- use bounded reasoning effort based on task difficulty and zero-cost constraints;
- preserve a machine-verifiable execution trace separate from private reasoning.

### Anthropic Claude

Verified product patterns:
- MCP is an open standard for connecting models to tools and data;
- Claude Research can break a request into smaller parts, investigate each, and return reports with citations;
- Artifacts separate substantial reusable output from the conversation;
- Anthropic recommends extended thinking over the older dedicated think-tool pattern for most uses.

ORIGIN design input:
- standardize tool/data connectors;
- keep artifacts separate and persistent;
- use explicit source citations for research;
- use internal reasoning capacity without storing or exposing raw chain-of-thought.

### Manus

Verified product patterns:
- each task can receive a fully isolated cloud virtual machine;
- the environment includes networking, filesystem, browser, and software tools;
- Browser Operator emphasizes auditability, one-time authorization, monitoring, takeover, and stop;
- Manus engineering describes context-aware tool availability and context engineering as key parts of agent reliability.

Not verified from the checked first-party material:
- a fixed three-agent Planner / Execution / Verification architecture as a universal Manus implementation detail.

ORIGIN design input:
- per-task isolated execution boundary;
- explicit authorization and takeover;
- context-aware tool availability;
- separate verification responsibility where ORIGIN can enforce it, without claiming it mirrors Manus internally.

## ORIGIN post-held-out architecture candidate

After the final unseen result is frozen, evaluate a five-stage answer pipeline:

1. Intent & Risk Classifier
   - classify task type, freshness need, evidence need, safety boundary, and expected deliverable.

2. Planner
   - produce a bounded task plan and evidence requirements.
   - no user-visible chain-of-thought.

3. Executor
   - call only allowed tools/providers.
   - preserve source/tool evidence, costs, failures, and timestamps.

4. Independent Verifier
   - check factual support, source coverage, contradictions, test/build evidence, and completion criteria.
   - verifier must be able to reject or request repair.

5. Presenter
   - produce the final answer/artifact using verified evidence.
   - clearly distinguish facts, assumptions, uncertainty, and next actions.

## Required evidence model

Each material answer claim should be able to point to one of:
- retrieved public source;
- connected/private source;
- deterministic tool output;
- verified code/test/build result;
- user-provided fact;
- explicitly labeled inference or assumption.

Unsupported material claims should fail closed or be labeled as unverified.

## Research loop candidate

Plan → Search → Read → Rank → Compare → Detect conflict → Fill gaps → Verify claims → Synthesize → Cite

Stop conditions:
- sufficient source coverage;
- diminishing evidence gain;
- source unavailable;
- zero-cost/provider limit reached;
- safety or privacy boundary reached.

## Coding loop candidate

Plan → Inspect → Patch → Typecheck/Lint → Test → Repair → Re-test → Verify diff/security → Deliver evidence

A coding task is not complete because a patch exists. Completion requires actual checks appropriate to the changed paths.

## User-visible transparency

Expose:
- current action;
- sources/files/tools used;
- verification result;
- blocked/failed/cancelled state;
- approval requests;
- changed files/tests/artifacts.

Do not expose:
- hidden chain-of-thought;
- invented percentage/ETA;
- unverifiable internal confidence claims.

## Evaluation plan after held-out

Do not tune against the official V1.4 final unseen corpus.

Create a separate answer-quality benchmark covering:
- factual QA with fresh web evidence;
- multi-source research and contradiction handling;
- long-form professional advice;
- code generation and repair;
- document/artifact generation;
- ambiguity handling;
- refusal/fail-closed behavior;
- source citation correctness.

Measure before/after on the same separate benchmark:
- factual support rate;
- citation support precision;
- contradiction detection;
- unsupported-claim rate;
- task completion rate;
- verification pass rate;
- repair success rate;
- user-actionability;
- latency;
- provider requests;
- total cost USD (must remain 0 for ORIGIN production policy).

## Release boundary

No runtime implementation from this document may land in main before V1.4 final unseen qualification is completed and its evidence is frozen.
