# ORIGIN 公開前品質・動作・UI/UX監査規定（必須）

**規定ID:** ORIGIN-REL-QA-001  
**適用範囲:** ORIGINの全機能・全リリース・本番公開・外部AI/外部委託/人間の作業を含むすべての変更  
**判定基準:** 総合合格率 **90%以上**、かつ重大項目は **100%合格**

## 1. 絶対ルール

1. **公開前に必ず実物を検査する。** コードを読んだだけ、スクリーンショットを一枚見ただけ、CIが緑だっただけでは、品質・動作・レイアウト・デザインの総合合格としない。
2. **不合格を直し、同じ監査を再実行する。** 初回の結果で終わらせず、指摘事項を修正した後、同じ対象・同じ条件・同じチェック項目で再検査する。変更による回帰も確認する。
3. **総合合格率90%以上の場合に限り、公開候補とする。** 90%未満は公開不可。重大項目に1件でも未解決・未検証があれば、総合点にかかわらず公開不可。
4. **証拠なしの合格・架空スコア・推測による完了報告は禁止。** 実行ログ、CI結果、テスト結果、実画面のキャプチャ/計測値など、判定を裏付ける証拠を記録する。実施できない項目は UNVERIFIED とし、合格扱いにしない。
5. **この規定は担当者やAIを問わず必須。** 引き継ぎ先のAI、エージェント、外部ベンダー、開発者は作業開始時に本規定を読み、作業計画・PR・引き継ぎ書に反映する。別の指示や短納期を理由に省略してはならない。
6. **検査合格はマージ/公開の承認ではない。** GitHubの main を正本とし、PR、マージ、デプロイはそれぞれ必要な承認・権限・既存の保護ルールに従う。無断でマージ・公開しない。
7. **費用・安全条件を維持する。** 監査や機能検証は既存の無料条件を守り、意図しない有料API、モデル、サービス、フォールバックを呼び出さない。費用が $0.00 と証明できない実行は行わず、UNVERIFIED として報告する。

## 2. 必須監査領域

各領域で、該当するチェック項目の合格/不合格/未検証を証拠とともに記録する。

- **機能・実動作:** 主要ユーザーフロー、入力/送信、応答、読み込み中、空状態、失敗/タイムアウト、再試行、履歴/保存、ナビゲーション、更新後の状態。正常系だけでなく異常系も検査する。
- **実画面レイアウト:** PC・タブレット・スマートフォンの実ブラウザ表示。少なくとも狭幅320px、360px、390px、412pxを含む対象ブレークポイントと、代表的なデスクトップ幅を確認する。縦方向のずれ、重なり、切れ、不要な空白、スクロール、キーボード表示時、セーフエリア、入力欄/ボタンの可視性・操作可能性を測る。
- **UI/UX・ビジュアル品質:** 情報階層、余白、整列、文字サイズ/行間、色のコントラスト、フォント、日本語の折返し、ボタンの位置/大きさ、フォーカス/ホバー/無効状態、エラーと進捗の伝わりやすさ、一貫性、認知負荷。基準画像または画面キャプチャと比較し、見た目だけでなく操作も確認する。
- **アクセシビリティ:** キーボード操作、フォーカス順/可視性、ラベル、セマンティクス、コントラスト、拡大/狭幅時の利用性。自動検査だけで合格としない。
- **回帰・テスト:** 関連ユニットテスト、統合テスト、E2Eを実行し、変更対象だけでなく主要既存フローへの回帰を確認する。必須CI、ビルド、型/静的検査、依存関係/セキュリティ検査も確認する。
- **信頼性・安全性・プライバシー:** 例外処理、データ保護、認証/権限、秘密情報の扱い、CSP/SRIなど既存のセキュリティ境界、誤った成功表示、未実装機能の誇張を確認する。
- **性能・安定性:** 初期表示、操作応答、不要な再レンダー/リクエスト、待機状態、タイムアウト、リソース負荷を、実測できる範囲で確認する。
- **費用・運用・公開整合:** 無料専用ポリシー、禁止された有料フォールバックの不存在、環境変数/設定、デプロイ対象SHA、ヘルスチェック、実際の公開先と表示内容の整合を確認する。公開後確認は承認済みデプロイ後に行う。

## 3. 合格率の計算とゲート

- 作業開始時に変更内容に応じたチェックリストを確定し、項目を重複計上しない。
- 合格率 = **合格項目数 ÷ 判定対象項目数 × 100**。UNVERIFIED と FAIL は合格数に含めない。対象外項目は理由を記録して分母から除外する。
- **公開候補の条件:** 合格率90%以上、重大項目100%合格、必須CI/E2Eが成功、重大な既知不具合ゼロ、再検査合格、証拠リンク/ログが揃っていること。
- **重大項目（例）:** 起動/主要フロー不能、入力欄や主要操作が隠れる/操作不能、データ損失、セキュリティ/プライバシー侵害、意図しない課金や有料フォールバック、誤解を招く成功/公開表示、リリース対象SHAの不一致。重大項目は全件解消・再検証必須。
- 90%という数値だけで品質を保証したと表現しない。残る不合格/未検証項目、リスク、除外理由を明記し、重大でなくても利用者に影響する項目はリリース判断者に開示する。

## 4. 必須の反復手順

1. 変更の目的・影響範囲・対象環境・無料条件を明記する。
2. 実行可能な監査チェックリストと合格条件を作成する。
3. 初回監査を実行し、各項目に PASS / FAIL / UNVERIFIED、証拠、重大度を記録する。
4. すべての失敗・重大リスクを修正し、修正内容とコミットを記録する。
5. **初回と同じチェックリスト・同じビューポート/ブラウザ条件で再監査**し、関連する回帰テストも再実行する。
6. 90%以上かつ重大項目100%合格になるまで、手順4〜5を繰り返す。達成できない場合は公開を止め、ブロッカーを報告する。
7. PRに監査結果、合格率の計算、証拠、未検証/残存リスク、テスト/CI結果を記載する。
8. リリース担当者が承認境界を確認する。承認前にマージ・デプロイ・公開を行わない。承認済み公開後は実際の本番URL、HTTP/ヘルス、デプロイSHA、実画面の主要フローを再確認し、結果を記録する。

## 5. PR/引き継ぎ時の必須報告テンプレート

- **対象/コミットSHA:**
- **変更目的・影響範囲:**
- **初回監査:** 合格/対象項目/合格率、FAIL、UNVERIFIED
- **修正内容:** 指摘、修正、コミット
- **同一条件での再監査:** 合格/対象項目/合格率、差分
- **重大項目:** 全件PASSの証拠、またはブロッカー
- **テスト/CI/E2E:** 実行したものと実結果
- **画面検証:** ブラウザ、ビューポート、証拠/計測値
- **費用・安全:** $0.00を確認できた根拠。未確認ならUNVERIFIED
- **残存リスク/対象外項目:**
- **状態:** CODE-PROVEN / TEST-COVERED / EXECUTED / UNVERIFIED
- **マージ/デプロイ:** 未実施/実施（承認と証拠を記載）

## 6. 最終原則

**「実物を検査 → 証拠を記録 → 修正 → 同じ検査を再実行 → 90%以上かつ重大項目100%を確認 → 承認後にのみ公開」**を、ORIGINの全変更に対する標準リリースゲートとする。
