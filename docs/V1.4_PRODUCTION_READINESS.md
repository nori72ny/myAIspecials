# V1.4 Production Readiness

This note records the live V1.4 production state separately from feature-design documentation. It is release evidence, not a parity claim.

## Verified production database state

The production Supabase project `origin-personal` already has the V1.4 durable coding migrations applied. Direct production verification confirmed:

- `origin_coding_jobs_v14` exists;
- `origin_coding_job_results_v14` exists;
- RLS is enabled on both V1.4 tables;
- the cancellation cleanup trigger exists;
- the current service-role-only design intentionally has no public/anon/authenticated RLS policies while direct privileges remain revoked.

Therefore database migration application is not the current production blocker.

## Current production blocker

The Vercel production runtime does not currently expose a parseable PostgreSQL connection URI through the supported candidates (`POSTGRES_URL`, `DATABASE_URL`, or `SUPABASE_DB_URL`). The shared V1.4 database URL resolver validates URL syntax, PostgreSQL protocol, and host and fails closed instead of accepting a malformed higher-priority value.

Until the production runtime has one valid PostgreSQL connection URI, `/api/coding/v1.4/status` truthfully reports the durable stores as unconfigured/unready even though the target Supabase schema itself is already live.

The temporary one-shot schema bootstrap was removed after direct Supabase verification. Production runtime logs should not emit the former schema-bootstrap `ERR_INVALID_URL` noise; ordinary V1.4 stores remain fail-closed when no valid database connection is configured.

## Additional prerequisites before enabling new autonomous jobs

After database connectivity is restored, all of the following must still be configured and verified before `ORIGIN_CODING_WORKER_ENABLED=true` is treated as release-ready:

- dedicated `ORIGIN_CODING_OPERATOR_SECRET` rather than legacy agent compatibility for broad/public exposure;
- the dedicated owner-HMAC secret used for stable owner binding;
- the AES data key used for private goals and encrypted result evidence;
- GitHub workflow dispatch configuration/token for the fixed hosted worker;
- exact-head end-to-end evidence from Coding UI → Vercel API → Supabase/Postgres → GitHub-hosted worker → zero-cost provider → isolated verification → encrypted result retrieval/cancellation.

Git publication and deployment remain separate, unauthorized capabilities in V1.4. Git write credentials must never enter the verification container.

## UI reconnect behavior

The Coding workspace supports reopening an existing opaque coding job ID after page reload. The operator supplies the job ID and Coding credential again; neither value is persisted to localStorage, sessionStorage, IndexedDB, or application logs.

Reconnect uses the same owner-scoped authenticated GET route as normal polling. If the durable job is active, the workspace resumes bounded polling and cancellation control using the credential held only in page memory. If the job is terminal, the workspace renders the stored encrypted-result projection when available and clears the in-memory credential.

The job ID format is validated client-side as `coding-` plus 22 URL-safe opaque characters before an authenticated job request is sent. The server remains authoritative for ownership and existence.
